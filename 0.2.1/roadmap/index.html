    Milestone Roadmap (M01-M53)¶

    This roadmap is generated from TASK_BOARD.md by scripts/build_docs_portal.py. It reflects the shipped milestones, the active backlog, and the exact project item backing each task.

    Executive Overview¶

    Verity Red Team evolved in six arcs. The first arc produced a standalone, stdlib-only MCP server and a zero-Docker workstation scanner — the minimum viable product that proves value in seconds. The second arc hardened the open-core boundary, shipped the free CLI, and published 0.2.0 to PyPI. The third arc closed every parity gap that a customer could hit in the field: offline mode, SSE transport, rug-pull detection, credential shapes, dialect-aware SQL guards, and container-verified end-to-end scenarios. The fourth arc turns the entire engineering record into a published documentation portal so adoption no longer depends on reading the source tree. The fifth arc aligns the product with reality: real-world Python AST rules, honest Pro CLI/MCP gates, and Tier 1/2 homepage and README parity. The sixth arc charts the next generation of the product: a unified verity scan CLI with SBOM and drift reporting, a local web viewer, interactive init/fix flows, opt-in semantic alignment, plugin hooks, Sigstore-verified snapshots, multi-framework agent SAST, and server reputation scoring.

    The invariant across all six arcs is the runtime abstraction barrier: core never imports enterprise code, and enterprise capabilities register through the verity.plugins entry point. Every milestone below respects that boundary, which is why the free distribution stays small and auditable while the commercial edition can layer additional detectors on top.

    Architectural Evolution¶

    The roadmap reads as a sequence of separations of concerns, each of which removed a class of coupling that would otherwise have blocked the next phase.

    1. Runtime separation (M01-M06). The plugin contract, the MCP server, the static screen, and the SQL AST guard were split into independently testable units behind typed dataclasses.
    2. Distribution separation (M07-M11). The CLI surface, the zero-dependency packaging, and the PyPI release decoupled the engine from any particular checkout or container runtime.
    3. Environment separation (M12-M37). Transports, offline mode, credential handling, and dialect awareness removed assumptions about network access, secret storage, and database vendor.
    4. Knowledge separation (M38). The documentation portal and the task-to-docs pipeline decouple what the engine does from how a customer learns about it.
    5. Product realism (M39-M45). Real-world Python AST rules, honest Pro CLI/MCP gates, and Tier 1/2 homepage and README parity keep the advertised capability identical to the shipped behaviour.
    6. Next-generation separation (M46-M53). The unified verity scan CLI (SBOM and drift), local web viewer, interactive init/fix, opt-in semantic alignment, plugin hooks, Sigstore-verified snapshots, multi-framework agent SAST, and reputation scoring extend the engine without breaking it.
